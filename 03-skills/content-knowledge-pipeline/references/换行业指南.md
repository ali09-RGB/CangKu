# 换行业指南

这份文档是「不写死」的落地说明。**换行业改 `domain.json`，不要改脚本。**

## 一、配置在哪

```
$WS/工具/domain.json        ← 唯一的领域配置
$WS/工具/domain.py          ← 加载器（一般不用动）
```

`domain.json` 存在时**完全接管**；不存在时脚本用内置兜底值（会警告）。所以它既是配置，也是权威来源。

查看当前配置：

```bash
cd "$WS/工具" && python domain.py --check
```

## 二、逐字段说明

### domain —— 这个领域叫什么

```json
"domain": {
  "id": "live-commerce",
  "name": "直播带货",
  "aliases": ["直播电商", "直播运营"],
  "what": "以直播间为场域的商品销售与运营方法论"
}
```

只用于显示与日志，不影响判定。但 `what` 写清楚很重要——**它是判断「这条算不算」的唯一一句话依据**，写模糊了后面所有词表都会飘。

### platform —— 跑在哪个平台

```json
"platform": {"id": "douyin", "name": "抖音", "note": "..."}
```

注意：**平台不在这里配置**。接口端点、CDP 截流、页面选择器在代码里，属于「平台适配层」。这个字段只是标记。

### judge —— 判定词表

```json
"judge": {
  "core": [],          // 领域定义性术语：命中任一即收（一票通过）
  "support": [],       // 宽泛词：命中 ≥2 个才收
  "negative": [],      // 领域相反：一票否决（如娱乐直播）
  "off_domain": [],    // 领域外的正当内容：一票否决（如平台处罚、售后）
  "hype": [],          // 标题党词：只降排序，绝不否决
  "author_hints": [],  // 作者名里的领域特征词，加分项
  "boundary": {}       // 边界规则，见下
}
```

写词表的三条经验：

1. **`core` 要放「领域定义性」的词，不是高频词。** 判断方法：把这个词单独拿出来，能不能说明「这条属于本领域」。
2. **`support` 是给 `core` 兜底的**，用来接住「一句话里没有术语但确实在讲这个领域」的内容。所以它需要成对出现。
3. **`hype` 只降权**。含「万能/必看」但内容有用的内容是真实存在的，设成一票否决会误杀。

### judge.boundary —— 边界规则（重点）

有些行业存在「形式相似但业务不同」的内容，需要在收进来之前排掉。这类规则放这里。

```json
"boundary": {
  "sv_ops": [],          // 排除项的动作词
  "sv_tag_strong": [],   // 单标签即可定性的
  "sv_mode": [],         // 「另一种业务模式」的词
  "live_specific": [],   // 本领域的专属语义词 —— 出现即豁免
  "live_common": [],     // 两边都用的词 —— 不能用来豁免
  ...
}
```

**语义：`boundary` 键存在即完全接管。** 写 `"boundary": {}` 表示「本行业没有这类边界规则」，所有边界词清空——不会回落成本行业之外的值。

> 这一条是刻意设计的：如果清空后回落，换行业会静默沿用上一个行业的排除词，造成大面积误判，而且没有任何报错。

**`live_specific` 与 `live_common` 的区别是这套规则成立的关键。**

| | 含义 | 用途 |
|---|---|---|
| `live_specific` | 只有本领域才会说的词 | 用来豁免（出现即说明是本领域内容） |
| `live_common` | 两边都在用的词 | **不能**用来豁免，否则规则失效 |

例：投放类内容在两个领域都讲，「投流」属 `live_common`；「直播间」「场观」属 `live_specific`。若用 `live_common` 做豁免，一条「短视频带货怎么投流」会被判成本领域内容——这正是要排除的。

### topics —— 主题分类

```json
"topics": [
  {"name": "选品排品", "priority": 1, "keywords": ["选品", "排品", ...]},
  {"name": "成交方法", "priority": 2, "keywords": [...]}
]
```

- `priority` 数字越小越优先，只在**多个主题得分相同时**裁决
- 数组顺序不影响判定，但**不要随意重排**（历史数据的主题归属会跟着变，看起来像 bug）
- 加主题只需在这里加一项，`pick.py` 的缺口加权会自动派生

主题设计建议：**按「决策环节」分，不要按「内容形式」分。** 前者稳定，后者随平台玩法变。9~10 个比较合适，太少检索粒度粗，太多每个主题都填不满。

#### 兜底主题：`fallback: true`

有些主题天生是「收容所」——比如直播带货里的「团队岗位」（中控 / 场控 / 面试 / 分工）。
它接的是别的主题都接不住的内容，关键词必然很泛（「团队」「中控」满屏都是）。

这种主题**不能参与正常竞争**。归类的规则是「按命中数比大小」，`priority` 只在并列时起作用；
泛词一比命中数就赢，会把真正讲投放、讲复盘的内容抢走。

```json
{"name": "团队岗位", "priority": 10, "fallback": true, "keywords": ["中控", "场控", ...]}
```

加了 `fallback: true` 之后，classify 先在所有**非兜底**主题里比，只有它们全部零命中，兜底主题才接管。
`domain.fallback_topics()` 负责把这份名单交给判定器。

> **实测代价**：直接加、不标 fallback，一次全库重判就改了 76 条归属，
> 其中 5 条已入库样本被归错（「千川全域四工具」被判成数据复盘）。见 D-32。

> **另一个坑**：关键词之间有包含关系时（「中控」与「中控王」），一个词会被算两次命中。
> 写词表前先自查一遍有没有互为子串的。

### keywords —— 搜索关键词

```json
"keywords": ["直播带货", "憋单", "千川投放"]
```

配合 `browse.py --kwfile domain` 使用。

设计原则见阶段二：**照缺口设计，并检验「这个词搜出来的主语是不是目标场域」。**

注释不能写在这个数组里（JSON 不支持）。要记录某个词为什么作废，写进 `_备注` 字段或项目决策记录。

### terms —— 术语校正

```json
"terms": {
  "replace": {"憋单错写": "憋单"},
  "flag_only": {"有歧义的词": "为什么存疑"}
}
```

按**本行业的 ASR 错法**写，不要照抄别的行业。`flag_only` 是只标注不替换，用于改错比不改更糟的情况。

### vault —— 知识库位置

```json
"vault": {
  "path": "C:/Users/.../【Obsidian】知识库",
  "report_dir": "10-视频报告",
  "home": "00-首页·知识地图.md",
  "index_dir": "20-方法论索引"
}
```

## 三、换行业的五个步骤

```bash
cd "$WS/工具"

# 1. 复制模板，改 domain 段（说清「这个领域是什么」）
cp ~/.workbuddy/skills/content-knowledge-pipeline/assets/domain.空模板.json domain.new.json

# 2. 写词表：core → support → negative → off_domain
#    先只写 20~30 个 core，够用就行，不要一次写全

# 3. 定主题：按决策环节分，5~9 个

# 4. 换配置，跑自测
mv domain.json domain.<旧行业>.json && mv domain.new.json domain.json
python domain.py --check
python classify.py --selftest        # 边界用例会大量失败，正常，见下

# 5. 重判全库（如果是复用旧库）或直接采集（新库）
python rejudge.py --dry --show-rejected 30
```

### 关于自测失败

`classify.py --selftest` 里的 `EXPECTED` / `BOUNDARY` 是**上一个行业的用例**，换行业后必然失败。两种处理：

- 保留旧用例，另外新增本行业用例（推荐，可以防止回退）
- 用本行业真实审批过的样本重建用例

自测用例本质是「这个行业什么该收、什么该拒」的断言，**换行业时它是最值得先写的东西**。

## 四、哪些情况必须改代码

配置能覆盖大部分，但这几种不行：

| 情况 | 要改哪 | 难度 |
|---|---|---|
| 边界规则的**判断逻辑**变了（不再是「作用对象」这一套） | `classify.py` 的 D-30 段 | 中 |
| 换平台（抖音 → 视频号/小红书） | `browse.py` / `sniff.js` / `extract.py` 的接口与选择器 | 大 |
| 媒体交付形态不同（如 HLS 切片流） | `extract.download_media` | 中 |
| 需要画面 OCR（字幕类内容） | 新增能力，目前没有 | 大 |

**只有前一种属于「换行业」，后三种属于「换平台」或「加能力」**，不要混为一谈。换行业不需要动平台层。

## 五、检查清单

换完之后逐条过：

- [ ] `domain.py --check` 显示的领域名、主题数、词表规模符合预期
- [ ] `classify.py --selftest` 的失败项**全部是本行业不适用**，没有「本该通过却失败」的
- [ ] **主题词与判定词要对齐**：写进 `topics` 的核心概念，`judge.core` 或 `support` 里也要有
- [ ] 拿 10 条本行业的真实内容手工过一遍判定，看 `reason` 是否说得通
- [ ] `boundary` 段：要么写成本行业的，要么显式写 `{}`，**不能留空不管**
- [ ] `vault.path` 指向新库，别写回旧库
- [ ] 抽 1 条跑完整四阶段，确认报告能落进新库的正确目录

> **第三条是实测踩出来的。** 换行业演练时，「拆家／训练」写进了 `topics` 却没写进 `judge`，
> 结果一条训练类内容被判成「不命中」——它能归类，但进不来。
> `topics` 决定「归到哪」，`judge` 决定「收不收」，**两套词表要各写一遍**。
