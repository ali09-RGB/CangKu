# 内容 → 知识库流水线

把「某个领域的内容平台上讲得好的视频」变成「能检索、会过期、有判断的知识库」。

这个技能不是一套写死的脚本，而是**一条可换行业的流水线**：引擎（采集/转写/判定/归档）不动，行业知识全部外置在 `domain.json`，平台差异隔离在适配层。

## 三层结构：先分清哪层该改

| 层 | 包含什么 | 换它要动什么 |
|---|---|---|
| **引擎层** | 采集→判定→提取→转写→写报告→归档的流程与脚本 | **不动** |
| **平台适配层** | CDP 截流、接口端点、登录态、页面选择器 | 换平台（抖音→视频号）才动，属改代码 |
| **领域配置层** | 判定词表、主题分类、搜索关键词、术语校正、知识库目录 | **改 `domain.json` 即可** |

这三层混在一起，就会出现「想换个行业，结果要改判定代码」的困境。

## 第一步：定位工作区（每次必做）

脚本不在技能里，在用户的工作区。**不要凭记忆硬编码路径**：

```bash
WS="C:/Users/wangl/WorkBuddy/2026-11-12-16-04-52/抖音知识流水线"
ls "$WS/工具/extract.py" >/dev/null 2>&1 || \
  WS=$(find "C:/Users/wangl/WorkBuddy" -name "00-项目决策记录.md" -path "*抖音知识流水线*" 2>/dev/null | head -1 | xargs dirname)
echo "工作区：$WS"
```

成功的标志是这四样同时存在：

| 路径 | 是什么 |
|---|---|
| `$WS/工具/` | 全部脚本 |
| `$WS/工具/domain.json` | **领域配置，换行业就改这个** |
| `$WS/阶段一-环境/data/db/pipeline.db` | SQLite 中转库 |
| `$WS/素材包/` | 每条视频一个目录（meta + 媒体 + 转写） |

## 四阶段总览

| 阶段 | 做什么 | 核心命令 | 详细步骤 |
|---|---|---|---|
| 一 · 环境 | 从裸机到能跑通一条链接 | 见参考文档 | `references/阶段一-环境搭建.md` |
| 二 · 采集 | 搜内容 → 判定 → 挑单 → 审批 | `browse.py` / `classify.py` / `rejudge.py` / `pick.py` | `references/阶段二-采集筛选.md` |
| 三 · 提取 | 下载媒体 → 转写 → 术语校正 → 写报告 | `batch.py` / `apply_terms.py` | `references/阶段三-提取与报告.md` |
| 四 · 归档 | 写库 → 同步 Obsidian → 索引 → 时效台账 | `sync.py` / `index.py` / `shelf.py` | `references/阶段四-归档.md` |

## 三条铁律（与行业无关，任何配置下都成立）

**一、改过判定配置，必须重判全库。**

```bash
python rejudge.py --dry                 # 先看影响
python rejudge.py --show-rejected 30    # 抽检被拒的，查误杀 ← 不能省
python rejudge.py                       # 确认后写库
```

只改配置不重判，库里的 `hit/topic/score` 还是旧规则算的，挑单照旧按旧分挑——等于白改。

**二、改配置，不要改代码。**

行业相关的东西一律放 `domain.json`。代码里的词表只是**兜底值**，配置存在时不起作用。改代码会让下一个行业继承你的临时决定。

**三、转写为空必须查清原因，不许凭标题写报告。**

转写为空有三种可能：提取失败（要重试）、真的没口播（如实记为无产出）、音频是音乐（同上）。**用标题推测内容凑一篇，是这条流水线里最严重的错误**，因为它会把编造的东西永久写进知识库。

## 换行业 / 换主题口径

改 `domain.json`，不要动脚本。字段含义、改动顺序、哪些情况必须改代码，见 `references/换行业指南.md`。

快速检查：

```bash
cd "$WS/工具"
python domain.py --check          # 看当前配置摘要
python classify.py --selftest     # 改完必须仍 100%
python rejudge.py --dry           # 再确认没误伤
```

| 「换个行业」 | 见 `references/换行业指南.md` |

# 换行业指南

这份文档是「不写死」的落地说明。**换行业改 `domain.json`，不要改脚本。**

## 一、配置在哪

```
$WS/工具/domain.json        ← 唯一的领域配置
$WS/工具/domain.py          ← 加载器（一般不用动）
```

`domain.json` 存在时**完全接管**；不存在时脚本用内置兜底值（会警告）。所以它既是配置，也是权威来源。

查看当前配置：

```bash
cd "$WS/工具" && python domain.py --check
```

## 二、逐字段说明

### domain —— 这个领域叫什么

```json
"domain": {
  "id": "live-commerce",
  "name": "直播带货",
  "aliases": ["直播电商", "直播运营"],
  "what": "以直播间为场域的商品销售与运营方法论"
}
```

只用于显示与日志，不影响判定。但 `what` 写清楚很重要——**它是判断「这条算不算」的唯一一句话依据**，写模糊了后面所有词表都会飘。

### platform —— 跑在哪个平台

```json
"platform": {"id": "douyin", "name": "抖音", "note": "..."}
```

注意：**平台不在这里配置**。接口端点、CDP 截流、页面选择器在代码里，属于「平台适配层」。这个字段只是标记。

### judge —— 判定词表

```json
"judge": {
  "core": [],          // 领域定义性术语：命中任一即收（一票通过）
  "support": [],       // 宽泛词：命中 ≥2 个才收
  "negative": [],      // 领域相反：一票否决（如娱乐直播）
  "off_domain": [],    // 领域外的正当内容：一票否决（如平台处罚、售后）
  "hype": [],          // 标题党词：只降排序，绝不否决
  "author_hints": [],  // 作者名里的领域特征词，加分项
  "boundary": {}       // 边界规则，见下
}
```

写词表的三条经验：

1. **`core` 要放「领域定义性」的词，不是高频词。** 判断方法：把这个词单独拿出来，能不能说明「这条属于本领域」。
2. **`support` 是给 `core` 兜底的**，用来接住「一句话里没有术语但确实在讲这个领域」的内容。所以它需要成对出现。
3. **`hype` 只降权**。含「万能/必看」但内容有用的内容是真实存在的，设成一票否决会误杀。

### judge.boundary —— 边界规则（重点）

有些行业存在「形式相似但业务不同」的内容，需要在收进来之前排掉。这类规则放这里。

```json
"boundary": {
  "sv_ops": [],          // 排除项的动作词
  "sv_tag_strong": [],   // 单标签即可定性的
  "sv_mode": [],         // 「另一种业务模式」的词
  "live_specific": [],   // 本领域的专属语义词 —— 出现即豁免
  "live_common": [],     // 两边都用的词 —— 不能用来豁免
  ...
}
```

**语义：`boundary` 键存在即完全接管。** 写 `"boundary": {}` 表示「本行业没有这类边界规则」，所有边界词清空——不会回落成本行业之外的值。

> 这一条是刻意设计的：如果清空后回落，换行业会静默沿用上一个行业的排除词，造成大面积误判，而且没有任何报错。

**`live_specific` 与 `live_common` 的区别是这套规则成立的关键。**

| | 含义 | 用途 |
|---|---|---|
| `live_specific` | 只有本领域才会说的词 | 用来豁免（出现即说明是本领域内容） |
| `live_common` | 两边都在用的词 | **不能**用来豁免，否则规则失效 |

例：投放类内容在两个领域都讲，「投流」属 `live_common`；「直播间」「场观」属 `live_specific`。若用 `live_common` 做豁免，一条「短视频带货怎么投流」会被判成本领域内容——这正是要排除的。

### topics —— 主题分类

```json
"topics": [
  {"name": "选品排品", "priority": 1, "keywords": ["选品", "排品", ...]},
  {"name": "成交方法", "priority": 2, "keywords": [...]}
]
```

- `priority` 数字越小越优先，只在**多个主题得分相同时**裁决
- 数组顺序不影响判定，但**不要随意重排**（历史数据的主题归属会跟着变，看起来像 bug）
- 加主题只需在这里加一项，`pick.py` 的缺口加权会自动派生

主题设计建议：**按「决策环节」分，不要按「内容形式」分。** 前者稳定，后者随平台玩法变。9 个左右比较合适，太少检索粒度粗，太多每个主题都填不满。

### keywords —— 搜索关键词

```json
"keywords": ["直播带货", "憋单", "千川投放"]
```

配合 `browse.py --kwfile domain` 使用。

设计原则见阶段二：**照缺口设计，并检验「这个词搜出来的主语是不是目标场域」。**

注释不能写在这个数组里（JSON 不支持）。要记录某个词为什么作废，写进 `_备注` 字段或项目决策记录。

### terms —— 术语校正

```json
"terms": {
  "replace": {"憋单错写": "憋单"},
  "flag_only": {"有歧义的词": "为什么存疑"}
}
```

按**本行业的 ASR 错法**写，不要照抄别的行业。`flag_only` 是只标注不替换，用于改错比不改更糟的情况。

### vault —— 知识库位置

```json
"vault": {
  "path": "C:/Users/.../【Obsidian】知识库",
  "report_dir": "10-视频报告",
  "home": "00-首页·知识地图.md",
  "index_dir": "20-方法论索引"
}
```

## 三、换行业的五个步骤

```bash
cd "$WS/工具"

# 1. 复制模板，改 domain 段（说清「这个领域是什么」）
cp ~/.workbuddy/skills/content-knowledge-pipeline/assets/domain.空模板.json domain.new.json

# 2. 写词表：core → support → negative → off_domain
#    先只写 20~30 个 core，够用就行，不要一次写全

# 3. 定主题：按决策环节分，5~9 个

# 4. 换配置，跑自测
mv domain.json domain.<旧行业>.json && mv domain.new.json domain.json
python domain.py --check
python classify.py --selftest        # 边界用例会大量失败，正常，见下

# 5. 重判全库（如果是复用旧库）或直接采集（新库）
python rejudge.py --dry --show-rejected 30
```

### 关于自测失败

`classify.py --selftest` 里的 `EXPECTED` / `BOUNDARY` 是**上一个行业的用例**，换行业后必然失败。两种处理：

- 保留旧用例，另外新增本行业用例（推荐，可以防止回退）
- 用本行业真实审批过的样本重建用例

自测用例本质是「这个行业什么该收、什么该拒」的断言，**换行业时它是最值得先写的东西**。

## 四、哪些情况必须改代码

配置能覆盖大部分，但这几种不行：

| 情况 | 要改哪 | 难度 |
|---|---|---|
| 边界规则的**判断逻辑**变了（不再是「作用对象」这一套） | `classify.py` 的 D-30 段 | 中 |
| 换平台（抖音 → 视频号/小红书） | `browse.py` / `sniff.js` / `extract.py` 的接口与选择器 | 大 |
| 媒体交付形态不同（如 HLS 切片流） | `extract.download_media` | 中 |
| 需要画面 OCR（字幕类内容） | 新增能力，目前没有 | 大 |

**只有前一种属于「换行业」，后三种属于「换平台」或「加能力」**，不要混为一谈。换行业不需要动平台层。

## 五、检查清单

换完之后逐条过：

- [ ] `domain.py --check` 显示的领域名、主题数、词表规模符合预期
- [ ] `classify.py --selftest` 的失败项**全部是本行业不适用**，没有「本该通过却失败」的
- [ ] **主题词与判定词要对齐**：写进 `topics` 的核心概念，`judge.core` 或 `support` 里也要有
- [ ] 拿 10 条本行业的真实内容手工过一遍判定，看 `reason` 是否说得通
- [ ] `boundary` 段：要么写成本行业的，要么显式写 `{}`，**不能留空不管**
- [ ] `vault.path` 指向新库，别写回旧库
- [ ] 抽 1 条跑完整四阶段，确认报告能落进新库的正确目录

> **第三条是实测踩出来的。** 换行业演练时，「拆家／训练」写进了 `topics` 却没写进 `judge`，
> 结果一条训练类内容被判成「不命中」——它能归类，但进不来。
> `topics` 决定「归到哪」，`judge` 决定「收不收」，**两套词表要各写一遍**。

# 阶段一 · 环境搭建

目标：在一台干净的 Windows 机器上，从零到**跑通一条链接的完整提取**。

验收标准只有一条：给一条分享链接，能产出「元数据 + 音频 + 转写文本」的素材包。达不到就不算搭好，不要急着进阶段二。

## 组件清单

| 组件 | 装在哪 | 为什么 |
|---|---|---|
| Python 3.13+ | 宿主 | 全部脚本 |
| Chromium（Playwright 自带）或 Chrome/Edge | 宿主 | CDP 截流必须有真浏览器 |
| Node.js | 宿主 | CDP 通信（`sniff.js`） |
| `faster-whisper` + 模型 | 宿主 | 语音转写，CPU 可跑 |
| SQLite | 宿主 | 中转库，单文件，无需服务 |
| Obsidian vault | 宿主 | 最终知识库 |
| n8n | 容器（可选） | 只做定时调度 |

**关键原则：凡是依赖宿主浏览器或大模型的，都不进容器。** 容器里没有浏览器，模型缓存也不该随容器重建而丢失。

## 步骤

### 1. Python 依赖

```bash
python -m pip install playwright faster-whisper av opencc-python-reimplemented
python -m playwright install chromium
```

`av` 是 PyAV，用来解容器里的音轨；`opencc` 做繁简统一。两者都不能省——ASR 有约 20% 概率整篇输出繁体，不做转换后面的术语规则一条都命中不了。

### 2. 模型（国内网络）

```bash
set HF_ENDPOINT=https://hf-mirror.com     # Git Bash: export HF_ENDPOINT=...
```

首次转写会自动下载 `small` 模型（约 500MB）。不设镜像大概率卡住且没有明确报错，表现成「一直没反应」。

### 3. 数据库

SQLite 单文件，首次运行脚本自动建表。主要几张：

| 表 | 作用 |
|---|---|
| `candidate` | 采集回的候选池（判定结果 + 审批状态） |
| `sample` | 已收录的样本 |
| `asset` | 素材文件登记 |
| `report` | 报告登记 |
| `feedback` | 审批反馈，负样本来源 |

### 4. 知识库目录

```
<vault>/
├── 00-首页·知识地图.md
├── 10-视频报告/<主题>/
├── 20-方法论索引/
├── 30-术语表/
└── 90-归档/
```

路径写进 `domain.json` 的 `vault.path`，或用环境变量 `KNOWLEDGE_VAULT` 覆盖（优先级更高）。

### 5. 宿主 HTTP 服务（只有用 n8n 才需要）

```bash
python service.py      # FastAPI，监听 8770
```

n8n 容器通过 `http://host.docker.internal:8770` 调它。

## 必须在开始前知道的四件事

**一、必须用有头模式。**
无头浏览器访问内容平台会被「验证码中间页」拦死，不是偶发，是稳定复现。不要试图绕过，直接用有头。

**二、登录判定只认会话 cookie。**
不要用 `csrf_token` 之类的字段判登录——匿名访客也有。只认 `sessionid` 非空，判完截图肉眼确认。

**三、n8n 的 Execute Command 节点没有 Python。**
「在 n8n 里直接跑 `python extract.py`」这条路走不通。所有重活放宿主服务，n8n 只发 HTTP 请求。

**四、容器不要挂载项目目录。**
n8n 只挂自己的数据目录。挂载越少，重建时越不会误删数据。所有文件读写都在宿主完成。

> Docker 引擎起不来时先看是不是虚拟化被安全策略拦了（某些环境下 `wsl.exe` 在禁用名单里）。这不是代码问题，需要人工启动 Docker Desktop。

## 验收

```bash
cd "$WS/工具"
python extract.py "https://www.douyin.com/video/<id>"
```

# 阶段三 · 提取与报告

目标：把审批通过的链接，变成一份**能被人直接用的知识报告**。

## 1. 批量提取

```bash
python batch.py --links links-batch5.txt
```

约 40 秒/条（含下载 + 转写）。单条重试用：

```bash
python extract.py "https://www.douyin.com/video/<id>"
```

产出在 `素材包/<video_id>/`：

| 文件 | 内容 |
|---|---|
| `meta.json` | 标题、作者、发布日、时长、互动数据 |
| `audio.m4a` 或 `video.mp4` | 媒体本体 |
| `transcript.raw.txt` | 原始转写（校正前） |
| `transcript.txt` | 校正后转写 |

## 2. 三种媒体交付形态（都必须兼容）

这是整条链路最容易出血的地方，出过三次事故，每次形态都不同：

| 形态 | 特征 | 处理 |
|---|---|---|
| ① 音视频分两条流 | URL 带 `media-audio` / `media-video` | 按 CDN 路径 hash 配对，**必须**加时长校验（预加载会导致音轨属于下一条视频） |
| ② URL 无标识，只有 mime | 全是 `audio/mp4` 之类 | 按 mime 判类，排除 UI 资源；音频缺失要抛异常 |
| ③ 音轨合进视频容器 | 全是 `video/mp4`，但容器里有音频轨 | **不要把「没有独立音频流」当失败**，直接把 `video.mp4` 交给转写 |

形态 ③ 的判断方法：下载一段查容器 atom（`mp4a` / `soun` / `esds` 存在即有音轨）。

统一入口是 `extract.audio_source(outdir)`：有 `audio.m4a` 用它，否则用 `video.mp4`，都没有返回 None。
`transcribe()` 本来就是 PyAV 解码，解 mp4 里的 AAC 是原生能力，**不需要额外写「抽取音频」**。

> 改这类逻辑时注意：同一个判断条件往往出现在多处（内层下载、外层调用、批量脚本）。
> **只改一处会造成静默失败**——日志全正常，只是转写没跑、`meta.json` 里少一个字段。这比崩溃危险。

## 3. 术语校正（不能省）

```bash
python apply_terms.py --all
```

规则来自 `domain.json` 的 `terms`（旧版 `terms.json` 作为回退）。

ASR 错误密度约 **1.2 处/千字**，且高度集中在专业术语。危害不是错字难看，而是**会让人做错动作**：

| 错 | 对 | 危害 |
|---|---|---|
| 别单 | 憋单 | 术语本身错 |
| 低增 | 递增 | 意思相反 |
| 空成本 | 控成本 | 后台选项不同 |

处理原则：

- 高置信度同音错 → 进 `terms.replace`，直接替换
- 有歧义的 → 进 `terms.flag_only`，**只标注不改**（改错比不改更糟）
- 原始输出保留在 `transcript.raw.txt`，随时可回溯

繁简统一在同一个环节做（`opencc` 的 t2s）。

## 4. 写报告

**先读转写，再写报告。** 顺序不能反。

结构参考既有报告：

```markdown
---
sample_no: S0NN
video_id: '...'
author: ...
topic: <domain.json 里的主题名>
publish_date: 2026-08-03
duration_sec: 312
likes: 1104          # 视频本身的点赞，不是作者累计
collects: 856
source: https://...
archived_at: 2026-11-13
---

# 标题

> 一句话讲这条视频的核心贡献

## 一、它讲了什么（结构还原）
## 二、可执行的部分（步骤/公式/阈值）
## 三、边界与前提（什么情况下不适用）
## 四、与库里已有内容的关系（互补/重复/冲突）
```

三条写作要求：

1. **区分「能长期用的」和「必须先核实的」**。判断维度、决策顺序、因果机制放前者；具体数字、阈值、按钮位置放后者。
2. **不美化**。内容薄就如实写「本条信息量有限，主要贡献是一个判断维度」。凑字数会污染知识库的信噪比。
3. **标注与其他篇的关系**。「与 S014 的四步相比多了两步」这类信息比内容本身更有检索价值。

## 5. 什么时候判定「这条没有内容」

转写为空不要立刻重试，先分清：

| 情况 | 判断方法 | 处理 |
|---|---|---|
| 提取失败 | 媒体文件缺失或极短 | 重试 |
| 纯音乐 / 无口播 | 关掉 VAD 复跑，结果仍是歌词或空 | 如实记为无产出 |
| 干货在字幕里 | 音频有内容但无人声语义 | 如实记为无产出（需要 OCR 才能拿，属能力缺口） |

**不许用标题推测内容凑一篇报告。** 这是这条流水线里最严重的错误——它把编造的东西永久写进知识库，而且看起来和真报告一模一样。

# 阶段二 · 采集筛选

目标：从平台捞回一批候选，判出「属于本领域」的，挑出「值得深挖」的，交人审批。

这一阶段的核心不是采集，是**判断**。

## 1. 登录

```bash
python browse.py --login      # 扫码，登录态存持久化 profile
python browse.py --status     # 检查登录 + 截图
```

只认 `sessionid` 非空。检查完一定看截图——状态字段说已登录、实际是游客页的情况出现过。

## 2. 设计关键词

**关键词照「缺口」设计，不是照「还能搜什么」。**

先看主题分布，挑最薄的 2~3 个主题打：

```bash
python domain.py --check     # 看主题与关键词规模
```

加词前过一道检验：

> **这个词搜出来的内容，主语更容易是「目标场域」还是「周边物」？**

以直播带货为例：目标是「直播间」，那么
- `新号开播` → 主语是直播间 ✅
- `养号` / `账号定位` / `新号起号` → 主语是账号 ❌（是另一条业务链）

一条补充判据：**一个词如果在所有同类内容上都出现，它就不携带信息。** 例如「电商运营」几乎是每条电商内容的默认标签，拿它做否决条件会误杀大片。

关键词写进 `domain.json` 的 `keywords` 数组，然后：

```bash
python browse.py --search --kwfile domain --per-kw-scrolls 2
```

也支持读 txt（`--kwfile keywords-batch3.txt`）。注释必须**独占一行**——解析器只跳过行首 `#`，行内备注会被当成关键词去搜。

## 3. 判定：两级放行

判定器回答两个**互不相干**的问题，混在一起会改出事故：

| 问题 | 由谁决定 | 改动影响 |
|---|---|---|
| 这条收不收 | `judge.core` / `support` / `negative` / `off_domain` | 命中池数量 |
| 归到哪个主题 | `topics` + `priority` | 只影响排序与检索 |

规则：

```
core 命中任意一个      → 收（一票通过）
support 命中 ≥ 2 个    → 收
negative 命中任意一个  → 拒（一票否决）
```

分数只用于排序，**不参与放行**。这是踩过坑的：早期用「强词凑分 ≥ 阈值」，结果词表没覆盖的明确相关内容全卡在阈值下漏判；而加一个词就能让一批无关内容跨过阈值。

`hype`（标题党词）**只降排序分，绝不否决**——含「万能/必看」但内容有用的视频真实存在。

### 边界规则

有些行业需要「排除法」：内容形式相似，但业务链路不同。这类规则写在 `judge.boundary`，**判定逻辑在 `classify.py` 里，允许少量改代码**。

判据的设计方法：不看关键词，看**方法论的作用对象**。作用在目标场域上就收，作用在周边物上就拒。

以直播带货为例：

| 作用对象 | 判定 |
|---|---|
| 直播间 | 收 |
| 短视频账号本身 | 拒 |
| 短视频挂车卖货 | 拒 |
| 获客 / 同城 / 老板 IP | 拒 |

之所以不能拉黑名单：「起号」「赛道」「对标账号」这些词两边都在用，必须看整句在说什么。

## 4. 重判（改配置后必做）

```bash
python rejudge.py --dry                 # 看影响，不写库
python rejudge.py --show-rejected 30    # 抽检被拒的 ← 这一步不能省
python rejudge.py                       # 确认后写库
```

`--show-rejected` 是发现「改过头」的唯一手段。两个真实的改过头例子都是靠它发现的：一个过泛的标签词一次误杀 25 条核心内容；一个两边通用的动作词误拒了投放教程。

## 5. 挑单

```bash
python pick.py --top 12 --batch 4
```

输出 `06-候选待审清单-N.md`，规则：

- 按主题缺口加权（篇数越少权重越高，从 `topics` 动态派生）
- 每主题最多 2 条、作者去重
- 自动标注「库里已有」和发布时长

**同质化是会加深的。** 判断信号：一批 12 条里有 5 条以上是「重复」而非「不相关」，说明这个主题挖到底了，应换方向而不是继续加量。

## 6. 审批落库

用户回编号后，把结果和**具体理由**写进库：

```python
con.execute('update candidate set verdict=? where video_id=?', ('accept', vid))
con.execute('insert into feedback(video_id,verdict,reason,created_at) values(?,?,?,?)',
            (vid, 'accept', '为什么收——要具体到内容，不要写"不错"', now))
```

理由会变成负样本，是画像演进的唯一原料。同时：

1. 清单文件头部改状态
2. `01-投喂样本库.md` 追加负样本编号
3. 生成 `links-batchN.txt`，进阶段三

## 「待定」是信号，不是垃圾

`hit=1` 但 `topic` 为空的候选，说明 `topics` 词表漏了东西。待定数量上涨，先抽查它，往往能在里面捞出好内容——比继续加关键词有效得多。

## 采集侧的无效信号

| 现象 | 原因 |
|---|---|
| 推荐流命中 0 条 | 新号推荐流不垂直，要养号；用搜索流 |
| 搜索间歇不发请求 | SPA 竞态，脚本要重试（回空白页 + 时间戳再进） |
| 同一批反复出现 | 去重依赖 `video_id`，`seen_count` 递增是正常的 |

# 阶段四 · 归档

目标：报告进库、能检索、知道什么时候会过期。

## 1. 写库并同步

```bash
python sync.py            # 素材包 + 报告 → SQLite + Obsidian
python sync.py --dry-run  # 先看会动哪些文件
```

`sync.py` 从 `domain.json` 读知识库路径与目录名（`vault.path` / `report_dir` / `index_dir`）。
`KNOWLEDGE_VAULT` 环境变量优先级更高，便于对比另一个库。

产出布局：

```
<vault>/<report_dir>/<主题>/S0NN-短名.md
```

## 2. 三个机械陷阱

**陷阱一：`sync.py` 只写入，不移动。**
改了 `topic` 后重跑 sync，新目录有了，**旧目录的文件还在**。结果知识库篇数比实际多。

> 改主题后的固定动作：`ls */<文件名>` 确认只有一个位置。

**陷阱二：库里的 `topic` 可能与内容不符。**
判定器按标题猜主题，长视频常猜错（讲投放的被判成数据复盘）。**以读完转写后的判断为准**，直接改库再 sync。

**陷阱三：首页是手工维护的。**
首页的统计数字（条数/字数/有效篇数）和篇目清单不会自动更新。新增报告后要手动改，否则首页会一直停在旧数字。

## 3. 索引

```bash
python index.py
```

重建样本索引表，写进 `01-投喂样本库.md` 的 `<!-- AUTO:INDEX:BEGIN/END -->` 标记区。

**这一段禁止手改**，下次运行会覆盖。手写索引出过错（把 2025 写成 2024，一年之差没人发现）。

## 4. 时效台账

```bash
python shelf.py           # 重算状态，写进 frontmatter
python shelf.py --check   # 巡检：哪些已超期、哪些快到
```

三级保质期：

| 级 | 类型 | 半衰期 | 判据 |
|---|---|---|---|
| A | 原理型 | 36 个月 | 依赖人的心理或决策顺序 |
| B | 方法论 | 12 个月 | 依赖平台机制 |
| C | 参数规则 | 3 个月 | 依赖后台按钮或具体数字 |

到期日 = 发布日 + 半衰期。

**混合型按最短的那段定级**，并在 note 里写清哪部分能信。例：「判断逻辑可长期用，但 20%/10% 两个阈值要按自己的数据校准」。

**一入库就已超期是正常的**，不是收录失误。品类红利按季度反转，后台参数按版本变。如实标注比假装它是新的更有价值。

状态三档：`现行有效` / `需复核`（到点了没人验证，**不代表错**）/ `已失效`（被新内容取代）。

状态**必须由日期算出来，不能手写**。手写的状态会和现实脱节，算出来的不会。

## 5. 首页

首页是知识库的入口，也是唯一需要人工维护的文件。新增报告后更新三处：

1. 顶部统计（条数 / 时长 / 字数 / 有效篇数）
2. 主题分组下的篇目清单（一行：篇名 + 核心句）
3. 如果有跨篇印证，补进「第一性原理」章节

**核心句写法**：一句话讲清这篇的独特判断，不要复述标题。例：
- 「追投不是加钱，是改速率——算出来比原来小，追了只会更慢」
- 「主播不行」不是原因，是放弃。能变成下一场动作的，才叫原因

## 6. 收尾核对

```bash
ls <vault>/*/S0NN*.md | wc -l     # 确认篇数
python shelf.py --check           # 确认没有意外的「已失效」
```

篇数对不上，先查重复文件（陷阱一），再查库里 `topic` 是否为空（会落到「未分类」）。
