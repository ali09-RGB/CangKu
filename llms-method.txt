# 抖音知识流水线 · 项目决策记录

> 长期项目。本文件记录**已敲定**的技术决策，凡已决策项不再重开讨论；新增决策按 D-编号追加。

---

## 一、项目目标

把「我感兴趣的抖音视频」自动变成「本地知识库里可检索的结构化报告」，全流程无人值守。

---

## 二、四阶段架构

| 阶段 | 名称 | 核心动作 | 产出 |
|------|------|----------|------|
| 一 | 基础环境配置 | 搭底座 | 可运行的容器化环境 |
| 二 | 兴趣理解 + 自主刷取 | 理解偏好 → 浏览抖音 → 命中即收藏 | 视频记录（统一契约） |
| 三 | 内容提取 + 报告生成 | 解析视频内容 → 产出报告 | 结构化报告 |
| 四 | 归档进知识库 | 报告写入 Obsidian | 可检索的知识条目 |

## 三、已敲定决策

### D-01 阶段二入口形态

- **敲定日期**：2026-11-12
- **决议**：分两步走。**一期采用 B · 网页版自动化**（Playwright 驱动本机已安装的 Edge，复用持久化登录态）；**二期切换为 C · 独立真机 + ADB**。
- **依据**：
  - 抖音开放平台**不提供个性化推荐流接口**，仅开放「自己账号的视频数据」「热点榜 hotsearch」「关键词视频检索 video.search（特殊权限）」，故 A 路线无法满足核心诉求。
  - 网页版自动化成本最低、无需额外硬件、有可参考的开源实现，适合优先验证全链路可行性。
  - 真机路线风控风险最低、App 端推荐流最真实，但需养号与硬件常驻，适合作为终态。
  - 已具备条件：闲置安卓手机、独立抖音小号、独立网络（流量卡/住宅 IP）、常开电脑。
- **硬约束**：入口模块必须与下游**完全解耦**。更换入口时，阶段三、四的代码不得改动。
- **统一输出契约（阶段二 → 阶段三）**：

```json
{
  "video_id": "",
  "share_url": "",
  "title": "",
  "author": "",
  "tags": [],
  "cover_url": "",
  "hit_reason": "",
  "prefilter_score": 0.0,
  "collected_at": ""
}
```

### D-02 收藏落点：双轨制

- **敲定日期**：2026-11-12
- **决议**：抖音侧低频、拟人节奏地收藏（随机间隔、随机停留时长、随机滑动距离）；同时在本地同步写入一条记录（D-01 契约结构），作为阶段三的**唯一数据源**。
- **理由**：抖音收藏夹有条数上限；高频规律性收藏本身是风控信号。
- **抗风险目标**：小号被封时已采集数据不丢失，流水线可从本地记录续跑，不中断。

### D-03 阶段二与阶段三的分工边界

- **敲定日期**：2026-11-12
- **决议**：阶段二只做**轻量初筛**（标题、标签、作者、封面 OCR、前 3 秒音频）；阶段三做**深度提取**（完整语音转写 + 画面理解）。**禁止阶段三重复初筛动作。**
- **理由**：判断「是否符合喜好」必须先获知内容，但完整提取成本高，存在循环依赖，必须在阶段二用低成本信号截断。

### D-04 偏好画像的数据来源

- **敲定日期**：2026-11-12
- **决议**：**人工投喂**，不做自动总结。投喂形式为**抖音分享链接**（由王总直接在对话中提供），由系统解析、落库、纳入画像。
- **样本策略**：初期**仅使用正样本**（王总喜欢的视频）。
- **风险与补偿**：仅正样本会导致偏好边界模糊、命中偏宽。补偿机制见 D-09 —— 闭环运行中「否掉」的动作会自动积累负样本，无需王总额外标注。
- **投喂样本库的双重角色（重要）**：
  1. **学习材料** —— 画像的构建依据
  2. **验收基准** —— 未来计算阶段二命中率的唯一量化标尺
  > 没有这批人工标注样本，后续的画像调优、模型选型、效果评估都将失去参照。因此**每条投喂样本必须持久化存档**。

### D-09 反馈闭环：画像持续演进

- **敲定日期**：2026-11-12
- **决议**：**建立闭环**。阶段二收藏的视频推送给王总后，王总的「点赞 / 否掉」作为修正信号回写画像，画像随之迭代。
- **副产物**：否掉的样本自动成为**负样本**，与 D-04 形成互补，边界逐步收敛。
- **对应**：这也使 D-07（触发节奏）需要考虑一个「反馈回收」环节。

### D-10 构建顺序调整：提取能力前置

- **敲定日期**：2026-11-12
- **背景**：D-04 要求 AI 读懂投喂样本才能建画像，而「读懂视频」属于阶段三的能力 —— 按 1→2→3→4 顺序实施会在阶段二卡住。
- **决议**：将**内容提取**做成一个**独立的原子能力**，**先于阶段二完成**。该能力同时服务：
  - 阶段二：解析投喂样本、建立偏好画像
  - 阶段三：解析收藏视频、生成报告
- **实际实施顺序**：一 → 提取能力 → 二 → 三（报告生成）→ 四
- **附带收益**：技术风险最高的部分（内容提取）被前置验证，比先搭架子更稳。

### D-12 投喂样本的解析方式

- **敲定日期**：2026-11-12（经实测验证）
- **决议**：`短链 → HTTP 302 取视频 ID → 无头浏览器渲染规范链接 → 从 meta / JSON-LD 提取元数据`。
- **实测结论**：纯 HTTP 请求**拿不到任何视频内容**；必须用真实浏览器执行 JS。详见「八、链接解析实测」。

### D-13 视频本体获取方案（关键突破）

- **敲定日期**：2026-11-12（经端到端实测验证）
- **决议**：使用 **CDP（Chrome DevTools Protocol）网络层截获**媒体流。
  - 以 `--remote-debugging-port` 启动无头浏览器 → 监听 `Network.responseReceived` → 捕获 `media-audio-*` / `media-video-*` 的 CDN 签名地址 → 带 `Referer` 整段下载。
- **为何不用其他路**：纯 HTTP 全死（0 字节 / 空壳）；`yt-dlp` 报「需要 fresh cookies」而爬虫拿不到有效 cookie；破解 `a_bogus` 签名维护成本高且易失效。CDP 方案**不碰签名**，让浏览器自己去请求，我们只负责在中间接住。
- **语音转写**：`faster-whisper` + `small` 模型（CPU int8），216 秒音频约 70 秒转完，中文识别置信度 1.00。
- **性能基准**：一条视频从链接到素材包完整产出 **96 秒**。
- **已知局限**：
  1. ASR 存在同音字错误，需配领域术语表校正（已在 S001 报告中建立首版词表）
  2. 画面信息（图表 / 板书 / 贴片文字）尚未做 OCR
  3. 媒体 URL 为时效签名，必须当次抓取当次下载，不能缓存复用

### D-14 转写后处理：术语校正不可省

- **敲定日期**：2026-11-12（经 8 条样本验证）
- **决议**：ASR 原始输出**不得直接入库**，必须经过「术语校正 + 繁简统一」两步后处理。
- **依据（实测数据）**：
  - 8 条样本 / 约 40 分钟音频 / 约 3.8 万字，识别出约 **45 类错误**
  - 错误密度约 **1.2 处 / 千字**，且**高度集中在专业术语**
  - 典型危害："别单→憋单"（术语本身错）、"低增→递增"（意思相反）、"空成本→控成本"（后台选项不同）、"追头→追投"（后台查无此项）
- **风险定性**：这不是文字瑕疵，而是**会直接导致读者做错动作**的错误。因此校正环节是质量红线，不是可选优化。
- **落地**：
  - 已建立 `03-术语校正词表.md`（含高危害词、批量替换表、存疑清单）
  - 术语表同时可作为 whisper `initial_prompt` 的领域提示，从源头降低错误率
  - 繁简统一已实现：`opencc-python-reimplemented`，已装并验证（`中共轉運營 → 中共转运营`）

### D-15 Python 提取能力以「宿主 HTTP 服务」形式暴露

- **敲定日期**：2026-11-12
- **决议**：Python 提取链路**不进容器**，以宿主上的 HTTP 服务形式暴露（建议端口 8770），n8n 容器通过 `http://host.docker.internal:8770/extract` 调用。
- **理由**：
  1. 提取链路**强依赖宿主上的 Chrome**（CDP 截流，见 D-13），容器内没有浏览器
  2. `faster-whisper` + `ctranslate2` 体积大、首次需拉模型，放容器会让镜像臃肿且重建时反复下载
  3. 模型缓存不应随容器生命周期消失
- **反面教训**：n8n 的 `Execute Command` 节点**默认没有 Python 环境**，所以"在 n8n 里直接跑 python extract.py"这条路走不通。这一点必须提前避开，否则会白搭一轮。

### D-16 偏好画像的判定核心：主题垂直度

- **敲定日期**：2026-11-12（王总明确）
- **决议**：王总投喂的偏好是**内容主题**，即「直播带货 / 直播运营」这一垂直领域，**不是**作者风格、表达方式或情绪偏好。
- **对阶段二的直接影响（重要）**：
  - 画像**不需要**建模复杂的美学/文风特征
  - 判定逻辑可简化为**领域相关性分类**：是否属于直播带货运营知识 → 是/否
  - 这意味着阶段二的初筛可以做得**又轻又准**，用标题 + 标签 + 作者 + 封面 OCR 的领域特征即可，不必上重型模型
- **副产物**：主题分类体系直接复用知识库的六分类（算法机制 / 流量节奏 / 成交方法 / 话术情绪 / 内容获客 / 付费投放）。

### D-18 n8n 不挂载项目文件，全部经宿主 HTTP 服务

- **敲定日期**：2026-11-12（实测确认，是对 D-15 的架构收敛）
- **决议**：n8n 容器**只挂载自身数据目录**（`C:\Users\wangl\n8n-local\n8n_data`），**不挂载** `/workspace`、`/vault` 等项目路径。所有文件读写（素材包 / 数据库 / 知识库）都在宿主 `service.py` 内完成，n8n 仅发起 HTTP 调用。
- **理由**：
  1. 原本计划的 `/workspace`、`/vault` 挂载**根本不需要**——既然文件操作都在宿主做，容器只是调度器
  2. 挂载越少，容器越无状态，重建时不会误删数据
  3. 路径含中文（`【Obsidian】直播带货知识库`），减少一层 Docker 路径解析的失败面
- **代价**：宿主服务必须常驻运行，开机要手动启动（已写入部署说明）
- **安全注意**：服务需绑 `0.0.0.0` 才能被容器访问，副作用是局域网内可访问 8770 端口，需靠 Windows 防火墙收敛

### D-19 阶段二采集改为「搜索流为主、推荐流为辅」双通道

- **敲定日期**：2026-11-12（真实运行后确认）
- **决议**：阶段二采集不依赖推荐流，主通道改为**关键词搜索流**（`general/search/single`），推荐流作为长期辅助（需养号）。
- **理由**：
  1. 实测未登录泛推荐流 60 条，判定命中 **0 条**——内容全是游戏/旅游/足球，新号推荐流根本不垂直
  2. 推荐流依赖账号历史，新号要养几天才会推直播带货内容，等不起
  3. 搜索流确定性高：单关键词稳定返回 24–35 条，命中率 86%
- **代价**：搜索流覆盖面受关键词表限制，可能漏掉未覆盖的细分话题。缓解方式：`keywords.txt` 可持续扩充；王总投喂新样本时，把样本里的高频标签补进关键词表。
- **二期预留**：可追加"种子作者通道"——用已投喂的 8 位作者主页作品扩散（本轮已发现晶姐、陈怼怼、唐Sir 等高频作者可作种子）。

### D-20 判定器改为「两级放行」规则

- **敲定日期**：2026-11-12（v1 在真实数据上暴露漏判后重构）
- **决议**：判定器不再用"强词凑分 ≥ 阈值"，改为：**核心词命中一个即通过；支撑词需命中 ≥2 个；负词一票否决**。分数只用于排序，不参与放行。
- **理由**：
  1. v1 把「直播复盘」「直播间留人」「逆向选品」「拉时长」等**明确相关**的视频全漏判了——这些核心术语根本没进词表，单强词 3 分 + 标签 2 分 = 5 分，卡在阈值 6 下
  2. "凑分"机制脆弱：加一个词就可能让一批无关内容跨过阈值，改词又会误伤另一批
  3. 两级规则语义清晰：核心词=领域定义，支撑词=辅证，可解释、可维护
- **同时新增负词表挡娱乐直播**：`娱乐直播 / 娱乐主播 / 才艺主播 / 游戏直播 / 秀场 / 陪玩 / 聊天主播`。这类内容大量使用「开播」「留人」「话术」，不挡会被大量误捞，而它与直播带货是两套知识体系。
- **效果**：自测 27/28 = 96%（边界+回归 20/20）；重评已入库的 274 条，**新捞回 15 条真实相关内容，同时踢掉 15 条娱乐主播噪音**——总数不变，精度提升。
- **已知天花板**：标题、标签、作者名全部零信号的视频无法判定（如"19-199，四马拖车"）。这是轻量初筛的固有局限，交给阶段三提取后归类。

### D-22 反馈闭环的落地方式：规则分流 + 表记录，不靠规则硬记个例

- **敲定日期**：2026-11-12（王总首次审批 12 条候选、否掉 3 条后）
- **决议**：把否决反馈拆成三层处理，**不把单条个例硬编码进规则**：
  1. **可归类的理由 → 写成规则**。本次两条理由落到两个不同机制：
     - 「太泛/标题党，没有具体方法」→ `HYPE` 词表，**只降排序分（-5/词），不否决**
     - 「不是直播带货核心知识」→ `OFF_DOMAIN` 词表（违禁词/平台规则/处罚/售后/鸡汤等），**一票否决**
  2. **不可归类的个例 → 只进 `feedback` 表**，候选表加 `verdict` 列（accept/reject）标记，规则不动。
  3. **禁止为单条视频改规则**，否则规则会膨胀成黑名单，失去泛化能力。
- **为什么标题党只能降权不能否决**：王总同时收下了「新人主播万能试镜公式，小白必看！！！」——它含"万能/必看"，但内容有用。若把标题党设为一票否决，会连带误杀这类真有方法的视频。
- **为什么有些否决归不了类**：第 12 条「用户给我们的容错极低，要学会抛钩子留住用户」被否，但它的标题、标签、作者（陈怼怼）**全部命中领域词**，光看元数据无法判断它"太泛"——必须看内容才知道。这就是轻量初筛的天花板，交给 `feedback` 表兜底，不硬塞规则。
- **一条重要修正**：陈怼怼是库里出现频次第 2 的作者（10 条），却被否掉一条。**说明"高频作者"不等于"内容好"**，二期"种子作者通道"不能只按作者产量选，要按历史通过率选。

### D-23 关键词表只放专业术语，不放泛词

- **敲定日期**：2026-11-12（第二批采集跑完后，按实测命中率得出）
- **证据**：同一批采集、同一个判定器，21 个关键词命中率从 0% 到 100% 完全有序——
  - 专业术语 80–100%：随心推 / 全域推广 / 素材追投 / 五维四率（100%）、开价 97%、逼单 96%、成交密度 94%
  - 泛词 0–60%：人设 41%、直播间搭建 36%、投产比 18%、直播切片 0%
- **结论**：**命中率由关键词的专业度决定，不是判定器的水平。** 泛词不会提高召回，
  只会灌进一批其他领域的内容再被判定器挡掉，白耗采集配额、拉低信噪比。
- **执行**：`直播切片` 整词作废（搜出来是剪辑教程，属剪辑技能而非运营知识）。
  「人设」「痛点」「直播间搭建」下次可剔除。
- **怎么找好词**：从**已有命中内容的 hashtag** 里挖，或直接取行业黑话（五维四率、
  随心推、成交密度）。凭空想的日常词一定是泛词。
- **⚠️ 2026-11-12 第三批补充：命中率是必要条件，不是充分条件。**
  「直播中控」命中率 87%，但命中的里面有「00 后中控不上班只兼职的一天」
  「盘点电商中控捧哏名场面」——**段子，不是方法**。专业词一样会带进娱乐内容，
  因为这类段子大量使用「中控」「主播」「运营」。已加娱乐负词组（名场面/搞笑/捧哏/
  belike/段子/沙雕/整活/精神状态）挡掉。**判定器要同时管「是不是这行」和「是不是干货」。**

### D-24 跨平台边界：直播带货不限平台，货架电商拒（已定）

- **敲定日期**：2026-11-12（王总原话：「现在主要是直播带货相关信息，包括抖音、视频号，
  但不限于这两个平台」）
- **触发**：第二批里「拼多多开店卡高投产+切车玩法」被判命中，但它是拼多多货架玩法。
- **决议分两层，处置相反**：

| 类型 | 处置 | 理由 |
|---|---|---|
| **直播带货，任何平台**（抖音/视频号/快手/小红书/淘宝直播/拼多多直播） | **都要收** | 直播带货的方法论是平台无关的：留人、成交密度、话术节奏、排品逻辑，换个平台照样用 |
| **货架电商玩法**（拼多多卡高投产、淘宝直通车、坑产、DSR、商品卡） | **拒** | 靠搜索排名和商品卡，跟直播的「实时流量节奏 + 即时成交」是两套逻辑 |

- **判据不能按平台名一刀切**——「拼多多直播」是真直播带货。所以：
  命中**货架电商专属词** 且全文**没有直播信号**（直播/开播/主播/上链接…）→ 才拒。
- **踩过的坑**：一开始把「高投产」放进货架电商词表，结果误杀一条千川内容
  （「只追高投产，可能丢了全域流量池」）——**千川也讲投产比**。
  已收紧为只保留拼多多特有的「卡高投产」。
  教训：判定词要看它在**目标领域里是否也常用**，不能只看它在别的领域也出现。

### D-25 第三类否决理由「内容重复」不能靠规则解决

- **敲定日期**：2026-11-12（第二批审批，4 条否决理由全是「重复」）
- **背景**：目前王总的否决已积累三类，**三类的处置方式完全不同**：

| 类型 | 例子 | 处置 | 能否用规则 |
|---|---|---|---|
| 太泛 / 标题党 | 「话术天花板」「超全」 | `HYPE` 词表降权 −5，不否决 | ✅ 可以 |
| 非核心知识 | 违禁词清单、平台规则 | `OFF_DOMAIN` 一票否决 | ✅ 可以 |
| **内容重复** | 「五维四率深度讲解」vs 已有 S015 | 只能标「库里已有」，人工判断 | ❌ **不行** |

- **为什么规则解决不了**：判定规则只看单条视频的标题/标签/作者，
  **它不知道库里已经有什么**。「五维四率」这条本身完全合格——垂直、专业、真的讲五维四率，
  规则没有任何理由拒绝它。它被拒的唯一原因是**我们已经有 S015 了**。
  这是「库的状态」问题，不是「内容质量」问题。
- **尝试过的自动化方案，全部失败**（记录在此避免重复踩）：
  - 标题字符二元组 Jaccard：同话题仅 0.05~0.09（「五维四率深度讲解」vs「5分教会你运营型中控如何看五维四率」，字面重合太少）
  - 领域术语集合 Jaccard：最高 0.25（泛词「直播间」撞所有样本，具体词又太少）
  - **标题层面根本判断不了「内容讲过没有」**。真正的解在阶段三：提取全文后做语义相似度，那时才有足够信息。
- **当前落地方式**：`pick.py` 在清单每行标注「库里已有 S015/五维四率」，
  由王总一眼判断。**不做伪精确的自动去重**——给一个假分数比如 0.35 反而误导。
- **挂起也是一种状态**：第 3 条「新号破冷启动3步」内容新但赞数低，王总未表态。
  这类**既不 accept 也不 reject**，保持 `verdict=null` 留在池里。
  强行记 reject 会污染负样本——它本身是干净的相关内容。

### D-26 时效性分级：知识必须有保质期

- **敲定日期**：2026-11-12（王总原话：「这条很关键，因为互联网上的时效性非常重要，
  这也是你要关注的重点」）
- **决议**：知识库里每一条都必须有**时效等级**和**到期日**，不再是「入库即永久有效」。
  落地在 `工具/shelf_life.json`（分级）＋ `工具/shelf.py`（算到期、生成台账）。

**三级分类，依据是「失效的驱动因素是什么」**：

| 级别 | 名称 | 半衰期 | 失效驱动 | 例子 |
|---|---|---|---|---|
| **A** | 原理型 | 36 个月 | 人性 / 机制 | 人性七宗罪、拉停留的认知缺口、要不要投流的决策框架 |
| **B** | 方法论 | 12 个月 | 打法被用烂 / 被平台压制 | 平播七步、软逼单结构、话术四步进阶 |
| **C** | 参数规则 | 3 个月 | 平台改版 / 新规 / 后台按钮变化 | 五维四率指标名、千川按钮操作、随心推参数 |

- **到期日 = 发布日 ＋ 半衰期，不是入库日 ＋ 半衰期。**
  一条 2025-09 讲随心推参数的视频，失效起点是它描述的那个平台状态，
  不是我们发现它的那天。按入库日算会**系统性高估新鲜度**。
- **状态三态，必须分清**：
  - `current` 现行有效
  - `review` 到点了但没人验证过，**不代表错**
  - `expired` 有明确证据失效（被新规推翻 / 被后续样本纠正）
  把后两者混为一谈，就会误删还有用的内容。
- **首个实例**：S001（5+2+1 憋单）标为 `expired`，被 S020 取代——
  S001 不是写错了，是**写的时候对、现在不对了**。这正是做这件事的原因：
  失效内容在库里和有效内容长得一模一样，看不出来。

**当前分布（23 篇）**：A 5 篇 / B 8 篇 / C 10 篇 ——
**参数型占了 44%**，这个结构本身是结论：直播带货领域的爆款内容大部分是「现在后台长什么样」，
三个月就要重写。**对采集策略的直接含义：C 类只在它是最近 3 个月内发布的才值得提取。**

### D-28 「点赞数」一直取错：那是账号累计获赞，不是视频点赞

- **发现日期**：2026-11-12（做时效性台账时，从索引表里看到同作者的视频点赞完全相同）

### D-29 主题定义分散在多处，是反复踩坑的病根

- **日期**：2026-11-12（第三批采集暴露出两个问题后归并）
- **现象**：新增「选品排品」「起号定位」两个主题后，出现两个独立的故障：

| 故障 | 表现 | 根因 |
|---|---|---|
| 新领域词命中率 0% | 「价格带」搜出 34 条，判定器一条都不收 | 只加了 `TOPICS`（归类用），没加 `CORE`/`SUPPORT`（放行用） |
| 新主题进不了清单 | 池内 119 条「选品排品」，清单里 0 条 | `pick.py` 的缺口加权硬编码了七个旧主题名 |

  `classify.TOPICS`（归类）、`classify.CORE/SUPPORT`（放行）、`pick.py` 的 `gap` 列表（收口加权）。
  **加一处忘一处**，而且忘掉时不会报错，只会静默地少收内容或少挑内容。

### D-30 短视频号运营不算命中：边界判据是「方法论的作用对象」

- **日期**：2026-11-12（王总一句「不算」定案）
- **原话**：「短视频运营内容（破播放量、账号权重）不算」
- **判据**（这是本条的关键，不是词表）：

| 方法论的作用对象 | 处置 | 例 |
|---|---|---|
| **直播间** | 收 | 直播新号破冷启动 3 步 / 直播前发什么短视频引流 / 直播间打标签 |
| **短视频账号本身** | 拒 | 新号一周涨粉破万 / 提高账号权重 / 播放量卡在 500 |
| **短视频挂车卖货**（另一条成交链路） | 拒 | 短视频带货选品 / 挂车日销千单 |

**为什么不能按词一票否决**：同一批词两边都在用。
「起号」「赛道」「账号定位」「对标账号」「破冷启动」直播在讲，短视频号也在讲。
实测「起号定位」主题 41 条候选里，一半是直播起号（该收），一半是自媒体做号（该拒）——
**光看标题里的词分不出来**。所以判据必须落在「作用对象」上，靠**直播实操语境**裁决。

- **落地**（`classify.py` 三级判，标题和标签分开算）：

| 级别 | 条件 | 理由 |
|---|---|---|
| 1 | 标题文案说了「短视频带货」，且标题无直播专属词 → 拒 | 「投流/千川」救不了，短视频带货也这么投 |
| 2 | 标题讲短视频号运营（涨粉/破播放/账号权重…），且标题无直播语境 → 拒 | 作者自己写的主语是账号 |
| 3 | 只有标签在说，且整条全无直播语境 → 拒 | 标签证据弱，必须叠加「完全没直播」 |

- **实测**：1384 条候选重判，**68 条命中→拒**（短视频带货模式 26 / 短视频号运营 40 / 仅标签 2），
  命中池 973 → 905。已认可的 24 条投喂样本**零误杀**，第 3 批清单 9 条全部仍命中。

#### 顺带挖出两个潜伏 bug（比 D-30 本身更值得记）

1. **跨标签假匹配**：标签拼接后 `_norm()` 删空格，`「视频号带货」+「视频号直播」`
   拼出 `「…带货视频号…」`，凭空出现「带货视频」——一条讲**视频号直播五维四率**的视频
   因此被判成短视频带货。修复：标签用 `|` 分隔，不删分隔符。
   这个 bug 一直潜伏在 `text` 的构造里，会影响所有词表匹配，只是恰好被 D-30 的判定放大才看见。
2. **@提及被当内容**：`@DOU+小助手` 让一条讲**淘宝生意参谋**的视频命中「dou+」，
   拒因跑偏到「短视频号运营」（它本来就该按货架电商拒）。修复：`BOILERPLATE` 加 `@[^\s#]{1,14}`。

#### 采集侧推论（治根，不只是判定侧）

短视频号运营内容占比这么高，根子在**搜索词**：凡是两边通用的词，搜出来短视频号内容占大头。
第 3 批关键词表里的 `养号`、`账号定位`、`新号起号`、`赛道选择`、`视频号带货` 全是这类，
已在 `工具/keywords-batch3.txt` 里标注作废并给出替代写法。**以后加关键词先过这一道**：
> 这个词搜出来的内容，主语更容易是「直播间」还是「账号」？

- **新增工具**：`工具/rejudge.py`——改词表后重判全库（`--dry` 预演、`--show-rejected N` 抽检误杀）。
  此前每次改词表都只影响"以后"，库里的 `hit/topic/score` 还是旧规则算的，清单照旧分挑——
  等于改了白改。并且手写 inline 脚本容易漏字段，出现「hit=0 但 reason 写着核心命中」的自相矛盾。

#### 第二轮（同日晚）：王总补一句「获客 / IP 也不算」

第 3 批审批时追问「短视频获客 / 老板IP 这类算不算」，答「不算」。据此再收一轮：

| 收窄项 | 结果 |
|---|---|
| 获客 / 同城 / IP 类（同城引流、老板IP、获客型短视频、人设故事、爆款结构、二创、编导、代运营） | 进 `SV_OPS`；`个人ip/老板ip/创始人ip/高客单ip/ip打造` 进 `SV_TAG_STRONG`（单标签即定性） |
| 做号动词（做账号 / 做新号 / 起新号 / 博主 / 从0粉 / 万粉） | 同上 |
| 泛电商（商品运营 / 商品管理 / 爆款打造） | 归入 `SHELF_ECOM` |

复判 **21 条命中→拒**，命中池 906 → 885（两轮合计 973 → 885，共 88 条）。
「内容获客」主题 20 → 11 条，剩下的是直播钩子/引流类。

**这一轮踩了两个「改过头」的坑，都是靠抽样核验才发现的，判据值得固化：**

1. **「电商运营」不能进 `SHELF_ECOM`**。它是几乎每条电商内容的默认标签，加进去一次拒掉 25 条，
   包括「千川全域投放详解」「新手必备千川技能-素材追投」这种直播投放核心内容。
   → **一个词如果在所有同类内容上都出现，它就不携带信息。** 高频 ≠ 有判别力。
2. **「快速起号」不能进 `SV_OPS`**。直播投放也讲「全域随心推如何投放，如何快速起号」，
   一条讲随心推的教程因此被拒。
   → **动作词要选「只有做号的人才会说」的那种**，两边都说的词不能用，无论它看起来多像。

**规则 2 同时收紧**：原来命中完整直播语境（含「千川/投流」）就能救回，
改为必须命中**直播专属词**（直播间/开播/场观/排品…）才救——
因为「投流」「千川」正是短视频带货最常用的词，它们救不了号运营内容。

## 七、视频本体获取攻坚记录（2026-11-12 · 已解决）

S001 首轮实测时只能拿到元数据，视频本体是空白，王总明确要求必须解决（"拿不到内容，知识库就是空的"）。以下是完整的攻坚过程与结论。

### 试过并失败的路

| 尝试 | 结果 |
|---|---|
| 纯 `curl` 请求分享页 / PC 页 | 只有 JS 空壳，无数据 |
| `yt-dlp`（2026.10.26）直解 | ❌ `ERROR: Fresh cookies (not necessarily logged in) are needed` |
| `curl` 取 cookie 再喂 `yt-dlp` | ❌ 只拿到 `__ac_nonce` 反爬标记，无有效 `ttwid`；仍报同样错误 |
| 反向解析签名 | 需破 `a_bogus`，维护成本高、随时失效，放弃 |

### 成功的路：CDP 网络层截流

1. 以 `--headless=new --remote-debugging-port=9222 --autoplay-policy=no-user-gesture-required` 启动浏览器
2. WebSocket 连 CDP，`Network.enable` 后导航到视频页
3. 监听 `Network.responseReceived`，捕获形如 `v11-weba.douyinvod.com/.../media-audio-und-mp4a/` 与 `media-video-avc1/` 的地址
4. 带 `Referer: https://www.douyin.com/` 整段下载
5. `faster-whisper` small 模型做中文转写

**核心思路：不破签名，让浏览器自己去请求，我们在中间接住。**

### 实测数据（S001）

| 指标 | 结果 |
|---|---|
| 音频 | 1.37 MB / 216.64 s / AAC 44.1kHz 立体声 |
| 视频 | 5.87 MB / 216.47 s / H.264 1080×1920 |
| 转写 | 143 段 / 3840 字 / 语言置信度 1.00 |
| 端到端耗时 | **96 秒**（含浏览器启动、20s 等待、下载、转写） |

### 副产品

- `工具/sniff.js` —— CDP 截流 + 元数据采集
- `工具/extract.py` —— 一站式编排（解析 ID → 截流 → 下载 → 转写 → 落 meta.json）
- `工具/README.md` —— 用法说明
- `02-视频报告/S001-5加2加1憋单法.md` —— **首份完整知识报告，含 ASR 术语校正表**

> 结论：阶段三的**技术风险已消除**。剩下的是"深度"选择题（D-05），不是"能不能"的问题。

### 提取：8/8 成功，但第 1 条触发了一个新 bug

前 7 条一次通过。第 1 条（海洋·曝光量）失败两次，报「截流结果里没有任何音频流（共 4 项）」。

### 顺带修掉一个归类盲区

抽查「待定」的 232 条时发现，里面有好内容被埋了：

## 十六、领域配置化（D-31 · 2026-11-13）

### 背景

王总要求把四阶段流程封装成 SKILL，且**直播行业的内容不要写死**，以后能换。
原来判定词表、主题、关键词、术语、库路径全散在代码里，换行业等于改代码。

### 决议：分三层，只把第三层做成配置

| 层 | 内容 | 换它要动什么 |
|---|---|---|
| 引擎层 | 采集→判定→提取→转写→报告→归档 | 不动 |
| 平台适配层 | CDP 截流、接口端点、选择器 | 换平台才动（属改代码） |
| 领域配置层 | 词表 / 主题 / 关键词 / 术语 / 库结构 | **改 domain.json** |

**关键区分**：「换行业」只动第三层；「换平台」才动第二层。两者不能混。

### 落地

| 文件 | 改动 |
|---|---|
| `工具/domain.json` | **新增**。从现有代码导出：CORE 53 / SUPPORT 52 / NEGATIVE 45 / 边界词 5 组 / 主题 9 / 关键词 64 / 术语 114 条 |
| `工具/domain.py` | **新增**。加载器，配置优先、代码兜底；配置缺失不崩 |
| `classify.py` | 词表注入层。内置词表降级为兜底值 |
| `sync.py` | 知识库路径与目录名改为读配置，`KNOWLEDGE_VAULT` 环境变量优先级最高 |
| `browse.py` | `--kwfile domain` 从配置读关键词 |
| `apply_terms.py` | 术语表优先读配置，回退 `terms.json` |

### 两个设计决定

**一、配置优先，代码兜底。**
配置删了流水线还能跑，但配置是权威来源。这样不会出现「忘了配就崩」，也不会出现「改代码绕过配置」。

**二、`boundary` 键存在即完全接管。**
换行业写 `"boundary": {}` 表示「本行业没有这类排除规则」，**不会回落成上一个行业的排除词**。
如果回落，换行业会静默沿用途上一行业的边界规则造成大面积误判，而且没有任何报错——
这是比报错更糟的失败模式。

### 验证

- 直播配置下 `--selftest` **49/49 = 100%**，与改造前一致
- 全库 1766 条重判：**hit 判定零变化**
- 4 条主题差异经查是历史手动改过 topic 的条目，用改造前代码复算结果相同，**与本次改造无关**
- 归档干跑 36 条路径正常

### 换行业演练（宠物喂养）

不写死这件事必须实测，不能只写文档。切了一套宠物配置验证：

- 猫粮内容 → 命中，归「喂养饮食」✅
- 直播憋单 / 千川投放 → 拒（`boundary: {}` 清空生效）✅
- **「狗狗拆家」第一次漏判**：support 只命中「狗狗」一个词，而「拆家／训练」只写在 topics 里、没进 judge

最后一条是这次演练最有价值的发现：**换行业时最容易犯的错，是把词写进了主题分类却忘了写进判定词表。**
主题词表只影响「归到哪」，判定词表才影响「收不收」——两者分开之后，这个错会变成静默漏判。
已在《换行业指南》的检查清单里加了这一条。

## 十七、第十个主题「团队岗位」与主题稳定性（D-32 · 2026-11-15）

### 背景

第 5 批采集后，「待定」涨到 **285 条，占命中的 21%**。抽样看不是词表漏词，而是**缺一个维度**：
中控 38 / 运营 82 / 团队 10 / 面试 8——全是「岗位与团队」类内容，9 个主题里没有一个接得住。
王总 2026-11-15 定：**加**。

### 决议一：加「团队岗位」，但它是**兜底主题**

第一次直接追加进 `topics`，`--selftest` 立刻红：

```
❌主题错 直播中控引路人  主题=团队岗位  期望=数据复盘
```

原因很蠢也很典型：关键词列了「中控」和「中控王」，**「中控王」里含「中控」，一个词被算两次**。

去掉重叠词后 selftest 回到 49/49，但全库重判改了 **76 条**归属，其中 5 条是**已入库样本**：

| 样本 | 原主题 | 被判成 | 问题 |
|---|---|---|---|
| S031 复盘判断链路四问 | 数据复盘 | 团队岗位 | 标题含「中控」 |
| S033 最后一小时动哪个变量 | 数据复盘 | 团队岗位 | 同上 |
| S036 千川全域四工具 | 付费投放 | **数据复盘** | 与本次改动无关，是历史配置漂移被一并纠正 |
| S032 标签跑偏四步修正 | 算法机制 | 起号定位 | 同上 |
| S037 开播前关同城 | 算法机制 | **None** | 之前的人工裁决被覆盖 |

根因：**主题归属是「按命中数比大小」，优先级只是并列时的裁判**。
「中控」在标题和标签里太常见，一比命中数就赢，把真正讲投放、讲复盘的内容抢走。

所以定两条规则：

1. **兜底主题不参与竞争**。配置里给主题加 `"fallback": true`，classify 先在所有非兜底主题里比，
   只有它们**全部零命中**时，兜底主题才接管。`domain.fallback_topics()` 提供这个集合。
2. **重判冻结已入库样本的主题**。`sample` 表里的主题是人工复筛后定的，
   报告已经写进知识库并按主题分目录——主题一漂移，知识库里就多一份旧目录副本。
   rejudge 现在只更新 hit/score/reason，topic 冻结。

校验结果：

- `--selftest` **49/49 = 100%**（改完两条规则后仍全绿）
- 全库 2094 条重判：**hit 判定零变化**（无新增误杀）
- 待定 285 → **227**；团队岗位 **55** 条；命中总数 1329 不变
- 5 条样本主题已人工恢复，重判后再跑一次为 **0 变化**（幂等）

### 决议二：知识库单段 frontmatter

原来知识库里每篇报告有**两段** YAML：本地 `02-视频报告/*.md` 自带一段（`sample / video_id / source`），
`sync.py` 又按数据库现算一段（时效字段）。直接相拼的后果：

- Obsidian 属性面板只读第一段，第二段变成正文里的垃圾
- 导出合订本时 `strip_frontmatter` 只剥一层，第二段漏进 `llms-*.txt`，把元数据塞进模型上下文

修法：`sync.strip_lead_frontmatter()` 在拼之前先剥掉正文自带的那段（只认「短且含冒号」的块，
避免把以水平线开头的正文误当 frontmatter）。全库 45 篇重写，校验：**45 个文件 / 45 个编号 / 零重复 /
零双段**；合订本里 `sample_no` 残留 0。

同时清掉了 8 份**旧主题目录副本**（主题漂移时 sync 只写新路径、不删旧路径留下的）。
按「不删只隔离」处理：移出知识库到 `抖音知识流水线/知识库旧副本_20261115/`，
Obsidian 里不再重名，文件也还在。

### 遗留

- 「待定」仍 227 条，多为标题信息不足（纯 hashtag、无实义标题），属正常状态，不是 bug
- `自媒体人` 未加进 `boundary.sv_tag_strong`——王总 2026-11-15 明确「不需要补」，
  理由是这类内容靠标题完整性已能被 D-30 拦住，加词会误伤「自媒体人转型直播」的正样本

## 十八、三处「静默漂移」的收口（D-33 · 2026-11-15）

都是同一种病：**一个值在多处各写一份，改了一处忘了另一处，程序不报错，只是慢慢变错。**

### 1. 样本主题卡在「未分类」

S024 / S028 / S034 三篇的 `sample.topic` 一直是 `未分类`，知识库文件也就一直躺在 `10-视频报告/未分类/`。
成因是早前重判时把 `topic='未分类'` 写进了 candidate 表（后来虽把 candidate 侧改回 NULL，sample 侧没跟着改）。
后果不只是目录难看：**`sync` 按 sample.topic 建目录**，所以只要这个值不对，文件就永远归不到主题里。

已改判为 `流量节奏`（三篇内容都是开场留人与接流），重新归档，`未分类/` 目录已空并删除。
**校验前置条件**：`select count(*) from sample where topic='未分类'` 必须为 0。

### 2. 被否决的视频被 sync 误登记为样本

第 7 批我在报告环节否决了「开播拉停留话术」，但素材包目录还在。
`sync` 的判据是「有 meta.json 就算一条样本」，于是自动登记成 `V164608`，
`index.py` 生成索引后那条挂在那儿，`shelf.py --check` 报「未登记 1 条」。

**这跟第 6 批转写为空那条是同一个坑，第二次踩。** 当时的解法是手动移目录，但没成规矩。
现在定：**素材包顶层只放「已收」的目录**，失败与被否决的分別移入 `_提取失败/`、`_已否决/`。
`sync` 不认下划线开头的目录作为样本来源这件事，后续要写进技能文档。

### 3. 分册抬头把「九大主题」写死了

加了第 10 个主题「团队岗位」之后，`export_online.py` 的 `SECTIONS` 里
`'九大主题的视频知识报告：流量节奏、…、起号定位'` 一个字没改，`llms-live-commerce.txt` 抬头一直是九个，
读这份合订本的模型会**以为库里只有九个主题**，第 10 个主题的内容等于隐身。

同类还有 `SOURCES['desc'] = '…36 篇视频报告…'`，早在 45 篇时就过期了。
两处都改成**生成时按实际目录统计**：

```
主题 = 10-视频报告/ 下的第一层目录名（正则取，不依赖分组键）
抬头 = 「共 N 篇视频报告，M 个主题：…」
```

现在输出：`共 62 篇视频报告，10 个主题：付费投放、内容获客、团队岗位、成交方法、数据复盘、流量节奏、算法机制、话术情绪、起号定位、选品排品`。

**教训**：凡是「数量」和「清单」，要么动态算，要么别写。写在常量里的一定会在某次扩容后变成假的。

### 校验脚本自身的坑

收口时写了个 frontmatter 检查，判据写成 `l.startswith('sample: ')`，结果 60 篇全报异常。
原因是**归档格式用的是 `sample_no:`**，`'sample_no: '` 并不以 `'sample: '` 开头。
数据没问题，是检查写错了。**校验脚本本身也要先自证**——先拿一篇已知正确的文件跑一遍，再信它的结论。

## 三、繁体输出问题

**现象**：S008（苏黎）、S010（小可）的转写整体输出为繁体中文，如「中共轉運營」「學牌品」「賽馬週期」「做直播代貨」「人貨廠」。

**原因**：whisper 在中文场景下会随机选择繁体/简体输出，与音频质量无关。**已出现 2 次 / 10 条，约 20% 概率，不能当偶发。**

**处置**：✅ **已在代码层解决**（2026-11-12）。`extract.py` 的 `transcribe()` 增加 `_t2s()` 后处理，用 `opencc` 逐段转简体，并统计转换段数写入日志。缺依赖时自动降级不转换，不阻断流程。

> ⚠️ **必须区分两件事**：繁简转换只解决字形（貨→货），**不解决同音字错误**（人貨廠 → 人货厂，正确是"人货场"）。字形和音误是两层，后者必须靠本词表。

## 四、行业专有名词（用于 whisper `initial_prompt` 领域提示）

这批词**不是错别字，是 whisper 压根不认识**——它们不出现在通用中文语料里，所以模型只能按音猜。把它们塞进 `initial_prompt` 能显著降低错误率。

### 直播运营

人货场、憋单、逼单、促单、塑品、货盘、排品、过品、测品、场观、千次观看、成交密度、停留时长、破层级、流量层级、开播、下播、控流速、追投、千川、全域推广、随心推、投产比、GPM、UV 价值、五维四率、数据化复盘、开口流量、急速流量

### 服装（S009 新增）

腰省量、余量、收窄、胯宽、下摆、面料、版型、硬面料、直线条

### 内衣（S009 新增）

侧比高度、鸡心位、跑背、漏空、托不住、移位、胸型

> **判断标准**：如果同一个词在通用语境里几乎不会出现，就值得进这张表。
> 「侧比」「腰省量」这类词，模型连猜都猜不对——它会给一个音近的常用词，读起来通顺但意思全错，**这种错误比明显错字更危险**。

## 三、四个硬结论（都踩过坑）

### 1. 无头模式彻底不可用

无头 Chrome 打开抖音，返回标题是**「验证码中间页」**，cookie 里只有反爬标记，
一个视频都拿不到。有头模式立刻正常（标题变「抖音精选电脑版」）。

→ 这个工具**不能后台静默跑，必须有窗口**。想做成定时任务，得允许弹窗。

### 2. 抓 DOM 这条路是死的

页面上 `a[href*="/video/"]` 数量是 **0**——卡片全靠 JS 点击事件，没有真实链接。
必须抓接口 JSON。

### 3. 登录判定不能用 `passport_csrf_token`

曾误报过一次：cookie 里 `passport_csrf_token` 存在（匿名访客也有），
但 `sessionid` 为空，脚本以为已登录，结果搜索页仍弹「登录后即可搜索」，
一条数据拿不到。

→ 唯一可靠标志是 `sessionid` / `sessionid_ss`。

### 4. 搜索页会「间歇性不发起请求」

连续 goto 不同关键词时，有时整页 **0 次** `general/search/single` 调用，
表现就是「抓到 0 条」。同一关键词单独重跑又正常——是 SPA 加载竞态，不是无结果。

→ 已加重试：先回 `about:blank` 强制全新加载；无响应则加时间戳参数重试，最多 2 次。
实测 12 个关键词中曾失败 3 个，加重试后全部成功。

## 四、判定器（classify.py）v2

### 为什么重构

v1 用「强词凑分 ≥ 6」放行。在真实搜索流上暴露大量**漏判**：

- 「一条视频九分钟教会你**直播复盘**到底看哪些数据」→ 漏判
- 「**直播间留人**四个关键」→ 漏判
- 「天才运营的逆向**选品**逻辑」→ 漏判
- 「新手直播千万不要盲目**拉时长**」→ 漏判

原因：这些核心术语根本没进词表，单强词只有 3 分 + 标签 2 分 = 5 分，卡在阈值下。

### v2 规则：两级放行

| 级别 | 作用 | 举例 |
|---|---|---|
| **核心词 CORE** | 领域定义性术语，**命中一个即通过** | 直播带货 / 憋单 / 千川 / 直播复盘 / 拉时长 / 选品 |
| **支撑词 SUPPORT** | 含义宽泛，**需命中 ≥2 个** | 直播间 / 开播 / 话术 / 复盘 / 留人 / 流量 |
| **负词 NEGATIVE** | **一票否决** | 娱乐直播 / 游戏直播 / 才艺主播 / 美食教程 |

分数只用于排序展示，不再参与放行——避免"凑分"这种脆弱机制。

### 娱乐直播必须拒

新增负词表专门挡这一类：`娱乐直播 / 娱乐主播 / 才艺主播 / 游戏直播 / 秀场 / 陪玩 / 聊天主播`。
它们是另一套知识体系，大量使用「开播」「留人」「话术」，不挡会被大量误捞。

### 自测结果

```
真样本命中     7 / 8      （唯一漏判：标题零信号的"19-199，四马拖车"）
主题准确       6 / 6
边界 + 回归   20 / 20     （含 6 条真实漏判回归 + 2 条娱乐直播必须拒）
合计正确率    27 / 28 = 96%
```

### 主题归类并列处理

`TOPICS` 各主题词数相同时，原先直接 `max()` 按字典顺序取，导致误归类：
「中控控单节奏…短视频追投不能停」因命中泛词「短视频」被归到**内容获客**，
实际是投放/流量主题。

已加 `TOPIC_PRIORITY` 做并列裁决，顺序为
**成交方法 → 流量节奏 → 付费投放 → 话术情绪 → 算法机制 → 内容获客**（越前越具体）。
generic 的「内容获客」放最后，避免它抢走具体主题。

### 关于那个 1 条漏判

阿瑞讲「19-199，四马拖车，了解下」——标题、标签、作者名**全部零信号**，
只有看内容才知道讲的是千川投放。

这是轻量初筛的**固有天花板**，不是 bug。处理方式：
在阶段二放宽为"高分的待定项也进候选池"，或等阶段三提取后再归类。

## 第 2 批采集（2026-11-12 晚 · 已完成）

### 为什么要换关键词

第一批 12 个词采完 274 条后，回头看已采内容的标签分布：`#直播带货` 86 次、
`#主播培训` 51 次、`#直播运营` 46 次——**说明这批词彼此高度重叠，采回来的是同一类内容**。
继续用它们只会重复，不会扩大覆盖面。

所以第二批换了 22 个「第一批完全没覆盖的细分术语」，按七个主题的缺口填空，
写入 `工具/keywords-batch2.txt`，用新加的 `--kwfile` 参数单独跑，
不与旧表混用（混用只会把旧内容再搜一遍）。

### 结果

| 指标 | 数值 |
|---|---|
| 关键词 | 21 个（`直播切片` 整词废弃，见下） |
| 耗时 | 9 分 23 秒 |
| 抓到 | 620 条 |
| 新入库 | 542 条 |
| 判定命中 | 471 条 |
| 候选池累计 | **816 条**（命中 630） |

两个关键词触发了重试（`开场话术`、`进入率`，都是「接口调用 0 次」的老毛病），
第 1 次重试均成功——SPA 加载竞态的重试机制有效。

### 一条重要规律：命中率由「关键词专业度」决定，不是判定器水平

各关键词命中率差异巨大，且排列完全有序：

| 关键词 | 命中率 | 关键词 | 命中率 |
|---|---|---|---|
| 随心推 / 全域推广 / 素材追投 / 五维四率 | **100%** | 直播间搭建 | 36% |
| 开价 | 97% | 投产比 | 18% |
| 逼单 | 96% | **直播切片** | **0%** |
| 成交密度 | 94% | 人设 | 41% |

**规律：专业术语词命中率 80–100%，泛词 0–60%。**

抽查验证了这个判断，两个低分词都拒得对：

- **`直播切片` 0%** —— 搜出来是「怎么剪辑」「切片授权」「AI 自动剪辑」，
  那是**剪辑技能**，不是直播带货运营知识。整词作废，不要再用。
- **`投产比` 18%** —— 被拒的是拼多多/淘宝的投产比算法（「拼多多运营」「保本投产比怎么算」），
  跟抖音直播带货不是一套体系。命中的那 22% 是千川 ROI。

**结论（已写进 D-23）：关键词表只放专业术语，不放泛词。**
泛词不会提高召回，只会灌进一批其他领域的内容让判定器挡掉，
白耗采集配额、拉低信噪比。「人设」「痛点」「直播间搭建」下次可以剔掉。

### 同时抓到一条误收

`投产比` 搜出来的「拼多多开店卡高投产+切车玩法撬动自然流量」被判为命中，
但它是**拼多多**玩法，不是抖音直播带货。

**这是判定器的一个真实盲区：它不区分平台。** 目前负词表里没有「拼多多/淘宝/天猫」。
要不要把「跨平台电商内容」判为非目标，取决于王总的偏好——如果他做的平台不限于抖音，
这类内容其实有价值。**列为待定项 D-24，不擅自决定。**

### ⛔ 两个新问题，都是「架构性的」，不是调参能修

**问题一：加了新主题，忘了加放行词 → 命中率 0%**

「价格带」0% 看着像"内容不相关"，实际是**判定器根本不认识这个词**。

原因是判定器有两套词表，职责不同：
- `CORE` / `SUPPORT` → 决定**放不放行**
- `TOPICS` → 决定**归到哪一类**

D-27 只加了 `TOPICS`，没加 `CORE`/`SUPPORT`，所以这些词只被归类、从不被放行。
已补进 `SUPPORT`（不补 `CORE`，因为这些词单独出现歧义大，
「赛道」可能是职业赛道，必须与另一个支撑词同现）。

**问题二：`pick.py` 里硬编码主题列表 → 新主题拿不到缺口加权**

`gap` 里写死了七个旧主题名，新增的「选品排品」虽然池里有 119 条、
库里 0 篇（缺口最大），却拿不到一分加成，**一条都进不了清单**。
已改成从 `TOPICS` 动态取。

> **这两条是同一个病根**：主题定义分散在多处，加一处忘一处。
> 判定器、收口脚本、归档脚本各自维护一份主题清单，迟早会打架。
> 现在的做法是尽量从单一来源（`TOPICS`）派生，但还没完全消除。

### 问题三：高命中率 ≠ 高质量

「直播中控」命中率 87%，但命中的里面有「00 后中控不上班只兼职的一天」
「盘点电商中控捧哏名场面」「这玩应不叫中控叫演员」——**是段子，不是方法**。

这类内容大量使用「中控」「主播」「运营」这些词，任何词表都挡不住。
已加一组娱乐负词：`名场面/搞笑/捧哏/belike/段子/沙雕/整活/精神状态`。
实测剔除 5 条，全部判断正确。

**D-23 需要修正**：之前说「命中率由关键词专业度决定」，
现在要补一句——**专业词也可能带来娱乐化内容，命中率是必要条件，不是充分条件。**

### 一个需要王总判断的边界

新收的 29 条里有不少是**短视频运营**而非直播运营：
「播放量卡在 500」「怎么找对标爆款视频破播放量」「提高账号权重」。

它们和直播带货有关（短视频能引流），但驱动力是另一套（完播率、涨粉）。
是否算命中，取决于王总要不要「短视频引流」这条线。**暂不擅自决定。**

# 提取链路故障复盘：串流与漏流（2026-11-12）

> **一句话**：7 条批量提取报「7/7 成功」，实际只有 5 条真的对。
> 1 条音轨是别人的（画面正确、声音错），1 条什么都没下到却标成功。
> **两个 bug 都会静默产出错误数据，是最危险的那一类。**

## Bug 1：串流 —— 一诺的视频里装着二占的声音

### 现象

一诺那条（`7652723325060129445`）的 `meta.json` 标题、作者、标签全对，
但 `transcript.txt` 的内容是二占那条（极速灌流）的逐字稿。

进一步比对发现：两条的 `audio.m4a` **字节数完全一致**（635015），
`transcript.txt` 的 md5 也完全一样。

### 根因

抖音网页版会**预加载上一条视频**。所以第二条截到的媒体列表里，前几项可能是上一条的流。

一诺那条的实际截流结果：

| 序 | 类型 | 域名 / 路径段 | 归属 |
|---|---|---|---|
| 0 | media-audio | v26-web / `785982…` / **`6af71d05`** | ← **二占的**（预加载残留） |
| 1 | (页面资源) | `douyin-pc-web/uuu_265.mp4` | 播放器 UI |
| 2 | media-audio | v11-weba / `3e08a37…` / **`6af71d3e`** | ← 自己的 |
| 3 | media-video | v11-weba / `99dcd2f…` / **`6af71d3e`** | ← 自己的 |

原逻辑是「列表里第一个 media-audio 就是音频」→ 取到了第 0 项（二占的）。
而视频取的是最后一个 → 取到了自己的。**结果画面对、声音错。**

### 修复：按路径段配对

音频和视频是同一视频的两条流，它们的 CDN 地址里**有一段完全相同的时间戳/hash**：

```
…/785982caea…/6af71d05/video/tos/…/media-audio-…
…/3ee5661643…/6af71d05/video/tos/…/media-video-…
                ^^^^^^^^ 这一段就是配对依据
```

现在 `download_media()` 取视频路径的第 2 段作为 key，
只从 key 相同的音频里选。一诺那条实测选中第 2 项（自己的），不再取第 0 项。

### 第二道防线：时长校验

`sniff.js` 本来就会抓页面播放器的 `videoTag.duration`。
现在把它传给 `download_media`，下载完音频后用 `probe_duration` 比对：

- 差异 > 3 秒 → **直接抛异常，中止，不产出数据**
- 差异 ≤ 3 秒 → 日志打「时长校验通过」

**宁可失败，也不要静默产出错的素材。** 知识库一旦被污染，后面所有报告都是错的。

## Bug 2：漏流 —— 贝奥那条什么都没下到，却标成 OK

### 现象

汇总里显示 `OK | 7608889703600770313 | -s | - 字`，
目录里只有 `meta.json` 和 `media.json`，没有音视频、没有转写。

### 根因

抖音有两种流交付形态，原代码只认第一种：

| 形态 | URL 特征 | mime |
|---|---|---|
| ① `douyinvod.com` | 路径里带 `media-audio` / `media-video` | video/mp4 |
| ② `sf26-sign.douyinstatic.com` | **URL 里没有任何标识** | **audio/mp4** |

贝奥那条全是形态 ②。原代码的两个过滤条件（`'media-audio' in url` / `'media-video' in url`）
一个都匹配不上 → 什么都没下载 → `files={}` → 但代码继续往下走、照样打印 `OK`。

### 修复

1. **按 mime 判类**，不再只看 URL：`audio/*` → 音频，`video/*` → 视频
2. **排除播放器 UI 资源**（`douyin-pc-web/uuu*`、`/obj/douyin-pc-web/`），否则会被误当成视频
3. **音频缺失直接抛异常**——音频是必需品，视频可选
4. `batch.py` 加结果校验：没有 `audio.m4a` 或转写为空 → 抛异常 → 归入 FAIL

## 历史数据核查

怀疑串流后，对全部 24 条素材包做了两项比对：

- 按 `audio.m4a` 字节数分组，找重复
- 按 `transcript.txt` 的 md5 找重复

**结果：只有这一对（二占/一诺）重复，此前 17 条全部干净。**
原因也清楚——前两批是逐条单独跑的（每条之间有别的事插入，预加载窗口没形成），
这批 7 条连续跑，才触发了预加载残留。

## 四条可复用的教训

1. **「第一个匹配」是危险的默认值。** 页面上存在预加载、缓存、竞态时，
   第一个不一定是当前的。取「最后一个」或「按特征配对」才可靠。
2. **成对出现的东西必须配对取。** 音频和视频分成两次独立选择，就必然有错配风险。
3. **一定有一道物理校验。** 时长对不上就是对的判据。这类校验不依赖任何解析逻辑，
   是最后一道保险。
4. **"成功"必须是验证过的，不是没报错。** 原来的 `if audio.exists(): 转写`
   隐含把「没有音频」当合法路径。没抛异常 ≠ 成功。

## Bug 3（不是 bug）：音轨合进视频容器 —— 海洋那条「没有音频流」

**时间**：2026-11-12 深夜，第 3 批提取
**现象**：截流 4 项全是 `video/mp4`，报「没有任何音频流」，重试两次同样失败。

### 排查过程

先怀疑网络和风控，都不是。把视频流下载下来查容器结构：

```
mp4a × 1   soun × 1   esds × 1
```

**音轨在视频里面。** 抖音把 AAC 音轨合进了 mp4 容器，CDN 完全不单独下发音频流。

前两次修复覆盖的分别是：
- D-13 的**串流**：有音频流，但要和视频配对（预加载导致取错）
- D-13 的**漏流**：有音频流，但 URL 没有 `media-audio` 标识，只能靠 mime 判类

这次是**第三种形态：压根没有独立音频流**。

### 修复

新增 `extract.audio_source(outdir)`，统一回答「拿什么去转写」：

```python
audio.m4a 存在 → 用它
否则 video.mp4 存在 → 用它（PyAV 能直接解容器里的 AAC）
都没有 → None
```

**关键认识：不需要「抽取音频」这个动作。**
`transcribe()` 本来就是 `av.open() + container.streams.audio[0]`，
PyAV 解 mp4 里的音轨是原生能力，直接把 `video.mp4` 交过去就行。
（第一版想复杂了，写了抽流逻辑，其实是多余动作。）

### 修复过程中踩的坑：条件改一半

第一版只改了内层判断：

```python
if not args.no_asr and (outdir / 'audio.m4a').exists():   # ← 外层没改
    src = audio_source(outdir)
```

结果：视频下载成功、**转写被静默跳过**，`meta.json` 里连 `transcript` 字段都没有。
日志一切正常，只有 meta 里少了一块。

**教训：同一个判断条件出现在多处时，必须一次全改。**
否则失败不会报错，只会**静默地少做一步**——这比直接崩溃更危险，
因为崩溃你会去看，静默你会以为它成功了。

## 不是 bug 的失败：纯音乐视频，无口播

**时间**：2026-11-13 凌晨，第 4 批提取第 5 条（运营主播知识分享·爆款排品逻辑）

**现象**：`转写结果为空，提取无效`，batch 判 FAIL。

### 排查

音频文件正常（641 KB），先怀疑是 VAD 过滤把内容滤掉了，关掉 VAD 重跑：

```
语言 zh 概率 1.00
段数 2
  詞曲 李宗盛
  詞曲 李宗盛
```

**这是一首歌。** 视频的干货靠**字幕**承载，没有口播。

### 结论

**这是正确行为，不是 bug。** `batch.py` 的「转写为空 → 判 FAIL」校验起了作用：
它拦住了「什么都没拿到却标成 OK」的情况（这正是 D-13 漏流那次踩过的坑）。

**能力边界**：这类「字幕 + BGM」视频和纯图文作品是同一个问题——
**内容不在音轨里**，需要 OCR 才能拿到。王总 2026-11-13 明确「图文方面先不要搞」，
所以这条按无产出处理，不硬凑报告。

**它暴露的筛选盲区**：标题看起来是硬干货（298 赞、221 藏），实际是纯音乐视频。
**标题和收藏数都不能保证内容在口播里。** 目前没有任何前置手段能在提取前发现这点，
只能在提取失败后如实记录。

> 若要降低损耗，可加一个轻量前置检测：转写为空时，判断音频是否含人声
> （如 VAD 有效语音占比 < 5% 直接判「无口播」），避免每次都要人工排查。
> 本次未做，留作待办。

## 六、复核怎么做

```bash
python 工具/shelf.py --check      # 日常巡检：只看过期和临期
python 工具/shelf.py              # 重新生成本台账
```

复核一篇 C 类内容，实际动作是：**把报告里的数字和后台对照一遍**。
对得上 → 改 `verified` 日期，续期；对不上 → 状态改 `expired`，写明被什么取代。

**注意区分 `review` 和 `expired`**：

- `review` = 到点了没人验证过，**不代表错**，可能完全有效
- `expired` = 有明确证据失效（被新规推翻 / 被后续样本纠正）

把这两个混为一谈，就会误删还有用的内容。
